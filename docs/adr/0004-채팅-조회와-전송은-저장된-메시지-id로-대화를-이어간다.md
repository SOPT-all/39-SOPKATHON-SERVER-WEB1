# 채팅 조회와 전송은 저장된 메시지 ID로 대화를 이어간다

## Context and Problem Statement

여러 학생이 같은 이야기의 마지막 장면을 보고 문장을 보낸다. 서버가 한 턴을 저장한 직후 연결이 끊기면 보낸 학생은 성공 응답을 받지 못한다. 이때 같은 문장을 다시 전송하면 이미 저장한 발화를 중복시킬 수 있다. 채팅 화면은 정상 전송 직후의 POST 응답과 재입장 시의 GET 응답으로 같은 대화를 재구성할 수 있어야 한다. [5번 조회 계약](https://app.notion.com/p/41f14af65e0681368214c6dac260425a) · [6번 전송 계약](https://app.notion.com/p/41f14af65e06812aba4bc3b79540d8bb)

## Considered Options

- **저장된 메시지 ID**를 전송과 조회에 공통으로 쓰면 학생 원문과 답변을 각각 식별하고, 같은 ID로 이전 기록의 경계도 지정할 수 있다.
- **페이지 오프셋**은 요청하기 쉽지만 새 전송이 들어오면 이미 읽은 페이지와 다음 페이지의 경계가 밀린다.
- **생성 시각**은 화면에 시간을 표시하기에 적합하지만 원문과 답변의 시각이 같을 때 순서를 확정할 보조 키가 필요하다.

## Decision Outcome

같은 이야기에서 커밋된 채팅 한 행을 메시지 한 건으로 취급한다. 6번 POST는 학생이 마지막으로 확인한 ID를 `lastSeenMessageId`로 받아 현재 대화와 비교한다. 성공하면 학생 원문과 답변을 저장 순서대로 반환한다. 5번 GET도 같은 행에서 `messageId`, `type`, `text`를 읽고 한 페이지 안에서는 ID 오름차순으로 반환한다. 정상 전송 직후에는 POST 응답을 순서대로 붙이고 이미 표시한 ID는 건너뛴다.

**응답 유실 시 복원 흐름**

1. 클라이언트는 입력 문장을 보존하고 커서 없이 GET해 최신 페이지를 다시 읽는다.
2. 전송이 커밋됐다면 학생 원문과 답변이 저장된 ID로 나타난다. 요청이 아직 처리 중이면 처음 조회에는 직전 장면만 보일 수 있다. 필요할 때 최신 페이지를 다시 확인하고, 그사이 30건을 넘겼다면 가장 오래된 ID를 `beforeMessageId`로 보내 이전 페이지를 읽는다.
3. 재전송은 사용자가 기록을 확인하고 다시 보내기를 선택한 경우에만 한다. 이때 화면에서 확인한 최신 메시지 ID를 보낸다. 같은 문장을 여러 학생이 쓸 수 있으므로 본문 일치만으로 특정 요청의 성공 여부를 단정할 수 없다.

이 계약을 보장하는 조회·저장 경계는 [Spring 트랜잭션 ADR](0005-spring에서-채팅-조회와-턴-저장의-트랜잭션-경계를-분리한다.md)에 기록한다.

### Consequences

- 이전 기록을 읽는 도중 새 턴이 추가돼도 이전 페이지의 ID 경계는 유지된다. 학생이 다시 접속해도 저장된 교정 피드백과 다음 장면을 같은 순서로 복원할 수 있다.
- 메시지 ID는 저장된 결과를 식별한다. 응답을 잃은 요청을 자동 재시도해도 한 번만 처리된다는 보장은 별도의 요청 식별·멱등성 설계가 필요하다.
- ID 순서를 대화 순서로 쓰려면 같은 이야기의 쓰기 요청이 직렬로 커밋돼야 한다. 여러 서버가 동시에 같은 이야기에 쓰거나 과거 메시지를 소급 삽입하게 되면 이야기별 순서 보장 방식을 다시 결정한다.
