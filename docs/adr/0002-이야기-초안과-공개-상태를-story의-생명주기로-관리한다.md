# 이야기 초안과 공개 상태를 Story의 생명주기로 관리한다

## Context and Problem Statement

음성 인식 원문에서 생성한 초안은 작성자의 편집을 거쳐 공개 이야기 하나로 확정된다. 녹음과 이야기는 1:1이며 초안과 확정 데이터의 편집 필드가 같다. 현재 요구에는 한 이야기의 여러 초안이나 편집 이력이 없다.

초안 생성 API는 원문·UUID와 생성 결과를 DB에 보관해야 한다. 확정 API는 최종 편집값으로 첫 장면과 질문을 생성한 뒤 첫 STORY 메시지와 함께 공개해야 한다. 초안 저장 위치를 정하면 생성·확정·공개 조회·재시도의 데이터 접근 규칙이 함께 달라진다.

원본 계약은 [팀 API 명세](https://app.notion.com/p/API-41f14af65e0680929a7aeb0ff586991f)와 사용자가 제공한 명세 본문을 따른다. [이슈 #19](https://github.com/SOPT-all/39-SOPKATHON-SERVER-WEB1/issues/19)는 이 결정에 기반한 첫 번째 API 작업이다.

## Considered Options

- 별도 story_draft 테이블에 초안을 저장하고 확정할 때 Record·Story를 생성한다.
- 같은 Record·Story를 유지하면서 Story의 상태로 초안과 공개를 구분한다.

## Decision Outcome

별도 초안 테이블을 추가하지 않고 Story에 문자열 enum 상태 DRAFT/PUBLISHED를 두는 방식을 선택한다. 한 초안이 한 이야기로 이어지는 현재 요구에 맞고, 같은 필드를 두 테이블에 복제하거나 확정 시 데이터를 옮기는 작업을 줄일 수 있다.

- 초안 생성 성공 시 최초 원문과 서버 발급 UUID를 Record에 보존하고, 편집 필드를 가진 Story(DRAFT)를 하나의 트랜잭션에서 저장한다. 첫 장면·질문·Chat은 아직 생성하지 않는다.
- 최초 원문과 UUID는 작성자의 편집값과 분리해 유지한다. UUID는 최종 등록과 재시도에 사용할 식별자이며 DB 유일성 제약으로 중복을 막는다.
- 후속 확정 API는 기존 UUID의 Story를 최종 편집값으로 갱신한다. 첫 장면 반영, 첫 장면과 질문을 포함한 STORY 메시지 한 건 저장, PUBLISHED 전환은 같은 트랜잭션으로 처리한다. Record·Story를 다시 생성하지 않는다.
- 외부 LLM 호출은 DB 저장 트랜잭션 밖에서 수행한다. 생성 실패 시 공개하지 않고, 확정 저장 실패 시 갱신·첫 메시지·상태 전환을 모두 롤백하여 DRAFT를 유지한다.
- 공개 목록·상세·학생 채팅은 PUBLISHED 이야기만 대상으로 한다. 초안은 직접 ID를 지정한 공개 조회에서도 노출하지 않는다.
- POST /api/v1/stories는 최종값을 받아 확정·공개 작업을 수행하는 기존 계약을 유지한다. 멱등성은 상태만으로 보장하지 않으며, 최종 요청 본문 비교와 처리 중 요청 조정은 확정 API에서 별도로 구현한다. AI 추천값과 첫 확정 요청의 편집값이 다른 것은 정상이다.

### Consequences

- Good, because 하나의 이야기 ID와 Record의 1:1 관계를 생성부터 공개까지 유지할 수 있다.
- Good, because 공통 편집 필드를 한 엔티티에서 관리하고 확정 시 데이터 복사를 줄인다.
- Bad, because 공개 조회마다 상태 조건이 필요하다. 공개 목록(#18)과 학생 메시지(#17) 등 후속 기능은 이 규칙을 반영해야 한다.
- Bad, because 초안에서는 첫 장면과 이미지 URL 등이 비어 있을 수 있다. 공개 전 필요한 값과 첫 메시지의 존재는 확정 서비스가 보장해야 한다.
- Bad, because 사용자가 확정하지 않은 DRAFT가 남는다. 보관·정리 정책과 다중 초안·버전 관리가 필요해지면 이 결정을 재검토한다.
- 기존 데이터가 있는 DB에 상태와 UUID 유일성 제약을 적용할 때는 기존 공개 여부·UUID 중복을 먼저 확인한다. 기존 행을 일괄 공개하거나 삭제하는 마이그레이션은 이 결정에 포함하지 않는다.
- 이번 첫 번째 API는 DRAFT 생성까지만 구현한다. 확정·공개 API의 재시도와 동시성 처리는 후속 범위이며 이 ADR 자체가 구현 완료를 의미하지 않는다.
