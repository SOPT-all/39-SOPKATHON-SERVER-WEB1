# 이야기 확정의 멱등성과 동시 요청을 DB에서 관리한다

## Context and Problem Statement

ADR 0002에 따라 초안과 공개 이야기는 같은 Story를 사용한다. 확정 요청은 같은 UUID·같은 필드값이면 최초 결과를 재사용하고, 처리 중이거나 공개된 키의 다른 본문은 409로 거부해야 한다. JSON 키 순서는 무관하며 최초 transcript도 비교 대상이다.

LLM 대기 동안 DB 트랜잭션을 유지하지 않으면서 여러 요청이 첫 장면·첫 STORY 메시지를 중복 생성하거나 공개하지 않도록 처리 권한과 실패 복구 방식을 정해야 한다. 서버 재시작과 오래된 처리자의 늦은 응답도 고려한다. 대상은 [이슈 #22](https://github.com/SOPT-all/39-SOPKATHON-SERVER-WEB1/issues/22)와 [확정 API 계약](https://app.notion.com/p/2-41f14af65e06811b8c47d915f86829c3)이다.

## Considered Options

- JVM 메모리 잠금·진행 중 Future만으로 요청을 합친다.
- DB 행 잠금을 LLM 호출과 확정이 끝날 때까지 유지한다.
- 짧은 DB 트랜잭션에서 요청 해시·처리 토큰·만료 시각을 기록하고 외부 호출 후 소유권을 다시 확인한다.

## Decision Outcome

세 번째 방식을 선택한다. 상태는 DRAFT/PUBLISHED를 유지하고 Story에 publish_request_hash, publish_attempt_token, publish_attempt_expires_at을 추가한다. 별도 테이블·Redis·JVM 단독 잠금은 사용하지 않는다.

- 검증된 본문의 최초 원문과 여섯 최종 편집값을 고정 순서로 직렬화하여 SHA-256 해시를 계산한다. 값의 공백·정규화는 변경하지 않는다. AI 초안 추천값과 첫 확정 요청이 다른 것은 정상이다.
- Story 행을 짧게 잠가 공개된 요청의 재사용·충돌을 확인하거나 DRAFT 처리 권한을 기록한다. 같은 진행 중 해시의 요청은 트랜잭션 밖에서 결과를 기다리며 다른 해시는 409이다.
- 처리 권한을 가진 요청만 LLM을 호출한다. 성공하면 새 트랜잭션에서 해시·토큰·유효 기간을 재확인하고 최종값·첫 장면·첫 STORY 메시지·PUBLISHED 전환을 함께 커밋한다. 기존 Record와 Story ID, 최초 원문은 유지한다.
- 실패하면 자신의 처리 표시만 해제하고 DRAFT를 유지한다. 실패한 시도를 기다리던 요청은 새 AI 생성을 자동 시작하지 않고 503으로 종료한다. 이후 별도 요청은 같은 키로 다시 시도할 수 있다.
- 중단된 시도는 만료 후 새 요청이 회수한다. 이전 토큰의 처리자는 만료·회수 뒤 저장하지 못한다. 공개 요청 해시는 이후 재시도를 위해 유지한다. 정리 실패가 최초 오류를 가리지 않게 하고 DB 장애 중 남은 표시는 만료로 복구한다.

### Consequences

- Good, because 같은 본문의 정상 동시 요청은 AI 호출을 공유하고 공개·첫 메시지를 한 번만 저장한다. 여러 인스턴스에서도 DB가 처리 권한을 조정한다.
- Good, because LLM 대기와 동일 요청 대기 동안 DB 잠금·트랜잭션을 점유하지 않는다.
- Bad, because 처리 표시·대기 시간·만료·소유권 검증이 필요하다. 만료 기간은 OpenAI 연결·응답 제한보다 여유 있게 잡는다.
- Bad, because 서버 중단이나 외부 응답 유실 후 AI 호출이 다시 발생할 수 있다. 외부 API와 DB 사이의 분산 트랜잭션은 제공하지 않으며 보장 대상은 중복 공개·첫 메시지 저장 방지이다.
- 확정 성공은 현재 계약의 201 CREATED, 같은 최종 본문 재사용은 200 SUCCESS이다. 없는 UUID는 404, 첫 확정의 원문 불일치는 400으로 명시한다. 이미 진행 중·공개된 요청의 본문 차이는 원문 차이를 포함하여 409로 우선 처리한다.
