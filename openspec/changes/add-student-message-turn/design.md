# Design

## Context

배포 워크플로는 기존 앱 컨테이너를 종료한 뒤 새 컨테이너를 기동한다. 해커톤에서는 하나의 앱 프로세스가 공유 이야기 전송을 처리한다고 가정한다.

## Goals / Non-Goals

같은 이야기의 전송만 직렬화하고, AI 응답을 기다리는 동안 DB 연결을 반납한다. 여러 앱 인스턴스 간의 선점 조율은 이번 범위에서 제외한다.

## Decisions

### 이야기별 전송 선점

앱 메모리에 처리 중인 이야기 ID를 원자적으로 등록한다. 이미 등록돼 있으면 `TURN_IN_PROGRESS`를 반환한다. 선점한 요청은 저장된 마지막 메시지 ID를 확인하고, 화면에서 받은 값과 다르면 `CHAT_OUTDATED`를 반환한다. 선점은 결과 저장 트랜잭션의 커밋 또는 롤백이 끝날 때까지 유지하고, 검증 오류와 AI 실패를 포함한 모든 종료 경로에서 해제한다.

MySQL 행 잠금은 AI 호출 동안 연결을 점유하고, DB에 처리 토큰을 두면 만료된 요청의 복구와 소유권 확인이 필요하다. 단일 프로세스 전제에서는 메모리 선점으로 같은 이야기의 중복 처리를 막을 수 있다.

### 문장 검사와 장면 생성의 분리

유효한 요청마다 현재 맥락을 읽고 동일 원문으로 교정과 장면 생성을 동시에 시작한다. 교정이 필요하면 장면의 성공·실패나 완료를 기다리지 않고 원문과 피드백만 저장한다. 교정이 통과하면 해당 요청의 장면과 기억만 저장한다. 수정 후 재전송은 새 요청이며 이전 생성을 재사용하지 않는다. 교정 실패 또는 통과 후 장면 생성 실패는 저장 없이 503을 반환한다.

한 번의 호출로 검사와 장면 생성을 처리하면 정상 턴의 대기 시간이 짧아질 수 있다. 두 단계를 나누면 자연스러운 구어체를 허용하는 교정 기준을 이야기 생성과 독립적으로 조정하고 검증할 수 있다.

### 교정과 스토리 생성 모델

3분 시연의 응답 시간을 고려해 교정과 장면 생성 모두 `gpt-6-luna`를 사용한다. 두 호출 모두 추론 수준은 none이다.

서비스는 `StoryAi` 인터페이스로 교정과 생성을 요청한다. `OpenAiStoryAi` 어댑터는 채팅 모델·프롬프트·출력 형식을 선택하고, 공통 `global.ai.openai.OpenAiChatClient`가 인증·HTTP 통신·JSON 파싱을 담당하며, 저장소는 채팅 패키지의 `GeneratedScene`을 받아 장면과 기억을 함께 저장한다.

### 장면 생성에 사용할 최근 대화

장면 생성 모델에 같은 이야기에서 완료된 최근 진행 턴을 최대 10개까지 시간순으로 전달한다. 한 턴은 학생 원문과 그 선택으로 만들어진 장면 한 쌍이다. 교정으로 끝난 원문과 피드백은 함께 제외한다. 이번 학생 입력은 별도로 전달하며, 완료된 진행 턴이 0~10개이면 등록된 첫 STORY를 시작 장면으로 한 번 전달한다. 11개부터는 시작 장면을 제외한다. STORY 채팅이 원본이며 세계관의 prologue를 중복 삽입하지 않는다.

5턴으로 줄이는 방안도 검토했다. 시연에서는 몇 장면 전에 나온 대사나 단서를 학생이 다시 언급할 때 원문을 활용할 수 있도록 10턴을 선택했다. 채팅 화면의 조회 페이지 크기와는 독립적으로 적용한다.

### 사건 전체 전달과 기록 단위

서버는 같은 이야기의 현재 인물 현황과 저장된 사건 전체를 조회한다. 장면 생성 모델이 이번 입력과 최근 장면에 관련된 사건을 선별해 사용한다. “그걸 돌려줄래요”처럼 물건 이름이 생략돼도 이전 사건을 참조할 수 있다. 해커톤에서는 키워드 추출, 검색 태그, 임베딩 인덱스를 도입하는 비용을 줄인다.

### 서버에서 관리할 프롬프트 두 개

기능별 기본 지침은 [교정](../../../src/main/resources/prompts/correction.yml)과 [장면 생성](../../../src/main/resources/prompts/scene.yml)에 둔다. 서버는 고정 지침과 요청별 입력을 분리한다.

- 교정 입력은 학생 원문이다. 자연스러운 단답·생략형을 허용하고 명백한 오류에만 교정 이유와 예시를 반환한다. 띄어쓰기만 틀리고 뜻이 분명하면 그대로 통과시킨다(예: ‘할수 있어요’).
- 장면 생성 입력에는 기존 인물 현황이 포함된다. 현황을 갱신하면 이번에 달라진 사실과 여전히 유효한 약속을 함께 반환한다. 변화가 없으면 갱신을 생략한다. 새 사건은 이번 장면에서 실제로 성립한 중요한 사실만 건별로 짧게 기록한다.
- 교정은 생성 상한 1,024토큰과 추론 수준 none을 사용한다. 글자 수는 프롬프트의 작성 가이드이며, 서버는 권장 길이를 넘긴 유효한 피드백도 전문을 저장하고 반환한다. 실제 모델 품질은 시연에서 확인한다. 구조 테스트는 모델 경계에서 실제 전송 본문과 저장 결과를 확인한다.

### 저장 경계

서버는 모델 출력을 검사한 후 저장한다. 교정은 두 채팅만, 진행은 두 채팅과 인물·사건 변경을 한 트랜잭션에 담는다. 인물 현황은 이야기당 최대 한 건으로 유지하고 새로운 사건은 각각 추가한다. 타임아웃이나 사용할 수 없는 모델 응답은 AI 처리 실패로 처리한다. 응답의 메시지 ID는 저장소에서 발급한 값을 사용한다.

## Risks / Trade-offs

앱 두 대가 동시에 같은 DB에 쓰면 프로세스별 선점 상태가 달라진다. 배포 구성을 다중 인스턴스로 바꿀 때 선점 방식을 다시 결정한다.

사건 전체를 보내므로 이야기가 길어질수록 입력량이 늘어난다. 시연에서는 사건 하나를 짧게 기록하고, 변화가 없는 턴에는 사건을 추가하지 않는다.

대안과 결정 배경은 [ADR 0003](../../../docs/adr/0003-공유-이야기의-교정과-장면-생성을-분리한다.md)에서 확인한다.
