# Design

## Context

앱은 EC2의 단일 컨테이너에서 실행되며 MySQL을 사용한다. prod 시작 시 data.sql을 읽고 기존 키가 있으면 대체로 원래 행을 보존한다. 현재 시드는 record 6건, story 6건, context 4건(1번 이야기 CHARACTER 1건·EVENT 3건), chat 10건(1번 이야기)이다. 일반 시작 동작과 초기화는 목적이 다르다.

## Goals / Non-Goals

클릭 한 번으로 실행 계획을 확인하고, 명시적으로 선택한 시연 범위만 배포된 버전의 기준 데이터로 되돌린다. 복원 대상은 행과 고정 시드 ID이며 스키마와 이후 자동 증가 번호는 유지한다.

## Decisions

- 시연 DB의 네 테이블 전체를 복원한다. 테스트로 만든 11번 이야기와 초안도 삭제 대상이다.
- 제안하는 진입점은 수동 workflow_dispatch의 preview(기본)와 reset이다. main에서만 실행하고 preview는 조회만 한다. reset에는 대상 이름의 명시적 확인을 요구한다. 기존 EC2 배포 시크릿과 저장소 변수 DEMO_DB_TARGET에 대상을 고정하고, 실행 중인 앱의 DB와 실제 접속 DB가 같은지 비교한다. 임의의 DB URL이나 SQL은 입력받지 않는다.
- EC2 내부에서 DB에 접속한다. CD와 같은 동시 실행 그룹(cd, cancel-in-progress: false)을 사용한다. 체크아웃한 SHA와 컨테이너의 배포 이미지 SHA가 일치해야 한다. preview는 대상, 시드 SHA, 테이블별 현재/예상 건수와 사라질 추가 이야기 ID를 요약한다. reset은 실행 직전 대상을 다시 확인한다.
- 전체 모드: 앱 쓰기를 잠시 중지하고 대상 테이블을 복원 가능한 형태로 백업한 다음 한 MySQL 세션의 트랜잭션 안에서 chat, context → story → record 순서로 DELETE한다. 먼저 배포 SHA의 data.sql로 임시 기준 테이블을 채우고, 트랜잭션 안에서 그 내용을 복사한다. 외래키 검사와 AUTO_INCREMENT는 유지한다. 비트랜잭션 테이블이나 암묵적 커밋을 일으키는 시드 DDL이 있으면 시작 전에 중단한다.
- 커밋 전에 기준 행의 ID·내용·참조까지 비교한다. 실패하면 롤백한다. 앱을 다시 시작한 뒤 목록·1번 상세·채팅 조회로 복구를 확인한다. 앱 중지 이후 오류에도 재기동을 시도하며, 커밋 이후 확인 실패는 별도 실패로 보고하고 백업으로 복구할 수 있게 한다.

## Risks / Trade-offs

전체 초기화는 이전 시연의 입력과 결과를 지우고 잠시 쓰기를 중단한다. 백업은 접근 제한된 위치에 두고 자격 증명이나 대화 본문은 Actions 로그에 남기지 않는다. 초기값 검증은 읽기 요청으로 끝낸다. 채팅 전송까지 검증하면 새 메시지가 저장되어 초기 상태가 달라진다.
